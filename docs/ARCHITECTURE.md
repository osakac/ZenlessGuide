# Архитектурные решения

Решения, принятые по ходу работы, и причины за ними — чтобы не переизобретать их заново. Текущий статус этапов — в [PLAN.md](PLAN.md).

## Структура

**Слой `views` вместо `pages`.** FSD-слой композиции страниц назван `views`: имя `pages` зарезервировано Next.js под Pages Router. Роуты в корневом `app/` остаются тонкими — файл маршрута только рендерит компонент из `src/views`.

**Границы слоёв проверяются автоматически.** Правила FSD (слой видит только нижележащие, кросс-импорты внутри слоя запрещены, обращение к слайсу только через его `index.ts`) — не договорённость на словах, а `eslint-plugin-boundaries` в [eslint.config.mjs](../eslint.config.mjs). Нарушение падает на `npm run lint`.

## Данные

**Весь доступ к данным изолирован в `src/shared/api`.** Ни один компонент не импортирует JSON напрямую. Все функции асинхронные, даже там, где сейчас читают файл синхронно, — переход на БД сведётся к замене тела функций и не заденет UI. Парсинг кешируется через `once()`, как и карта персонажей по id (`loadCharactersById` — внутренняя для `shared/api`, её используют склейка команд и тир-листа, наружу через `index.ts` не отдаётся). Публичный API — только то, что вызывают страницы: `parse*File` тесты берут прямо из `schemas.ts`. `getTierBoard` возвращает массив групп `TierGroup[]`, без обёртки `{ groups }`.

**zod-схемы — источник правды по форме данных.** Типы выводятся из схем через `z.infer`, поэтому валидация и типы не расходятся. Ошибка в JSON падает с указанием конкретного поля, а не где-то в глубине рендера.

**Поля билд-гайда опциональны.** Данные наполняются итеративно, и страница агента должна корректно рендериться с частично заполненной записью: блок без данных просто не отрисовывается, а если пусто всё — показывается заглушка. Исключение — блок «Команды»: он виден всегда, а без составов пишет «Возможных команд на данный момент нет». Команды не поле гайда, а выборка из общего `teams.json`, и пустая выборка — тоже информация для читателя, а не незаполненные данные; поэтому на решение «гайд ещё не написан» блок не влияет и выводится под заглушкой.

**Тир в проекте — решение, а не слепок с prydwen.gg.** На prydwen.gg только два верхних тира (T0, T0.5) соответствуют нашим S/A; T1 и ниже места в проекте пока не имеют. Агент из T1 заводится тиром A по явному решению пользователя на этапе добавления (так для Вивиан, T1 → A) — автоматически понижать его до T1/T2 или заводить новый тир скилл не должен, это каждый раз отдельный вопрос.

**Роль в тир-листе — свойство записи, а не персонажа.** `pure-dps` / `anomaly-dps` / `support` лежат в `tierlist.json`, потому что это место агента в конкретной оценке: один и тот же агент бывает основным ДД в одной мете и саб-ДД в другой.

**Иконка и цвет роли позаимствованы у тир-листа prydwen.gg.** Заголовки колонок Pure DPS / Anomaly DPS / Support используют те же значки (`HandFist` / `Ghost` / `FlaskConical` из `lucide-react` — визуальные аналоги иконок FontAwesome с prydwen) и тот же цвет текста (`--role-pure-dps` #ed343e, `--role-anomaly-dps` #c267ec, `--role-support` #7cde97 в [globals.css](../src/app/styles/globals.css)), что и на prydwen.gg — читатели, знакомые с их тир-листом, узнают категории сразу. Сопоставление роль → иконка/цвет/класс бейджа лежит в `shared/lib/role-styles.tsx`, а не в `entities/tier`: тот же набор ролей нужен и бейджу типа урона на карточке состава (`entities/team`), а слои `entities` друг у друга ничего не импортируют — общее ушло в `shared`.

**Тип урона состава — необязательное поле команды, не пятая роль тир-листа.** `damageType` в `teamSchema` — `pure-dps` или `anomaly-dps`, только два значения (список — `teamDamageTypes` в `shared/config/team-damage-types.ts`, схема строит из него `z.enum`): это не позиция конкретного агента (как `role` в `tierlist.json`), а то, чем состав в целом преимущественно наносит урон. У `support`-варианта здесь смысла нет — состав без ДД не бывает. Поле опционально, как остальные необязательные части данных: составы размечаются по одному, пока не пройдены все пятнадцать. Бейдж рисуется в `entities/team/ui/team-card.tsx` тем же цветом и подписью, что и колонки тир-листа (`getTierRoleLabel`, `getRoleBadgeStyle` из `shared`), чтобы двух значений не пришлось переизобретать заново.

**Карточка состава — `bg-card`, а не фон страницы.** Изначально карточка лежала прямо на фоне страницы (`bg-background`) без какой-либо глубины, а бейдж типа урона висел абсолютным пиксельным пятном на углу — на карточках без бейджа это смотрелось неровно. Сейчас бейдж — обычный элемент в шапке карточки, слева (`justify-start`, без `absolute`). Пробовали добавить между портретами `ChevronRight` (как в `skillPriority`), намекая на порядок ротации, — визуально было лишним, вернули обычную сетку 3×1.

**Иконка роли рисуется функцией, а не отдаётся компонентом.** `renderRoleIcon(role, className)` в `shared/lib/role-styles.tsx` возвращает готовый `ReactNode`, а не `LucideIcon`-компонент из словаря; `getRoleIcon` удалён, и `tier-board` тоже рисует иконки через `renderRoleIcon`. Так было не всегда: карточка состава сперва делала `const Icon = getRoleIcon(damageType)` и рендерила `<Icon />` — ровно тот же приём, что уже жил в `tier-board.tsx`. Но там переменная объявлена внутри `.map()`, а в `TeamCard` — прямо в теле компонента, и `eslint-plugin-react-hooks` (правило `static-components`, компилятор React) ругается именно на второй случай: «Cannot create components during render», — компонент, вычисленный вызовом функции в теле рендера, компилятор не отличает от нестабильной фабрики. Проще было спрятать вызов внутри обычной (не-PascalCase) функции, чем чинить компилятор.

**Команда — самостоятельная запись, а не поле агента.** Составы лежат в `data/teams.json`, участники указаны по `id` агентов. Связь «агент ↔ команда» не хранится, а выводится: команда принадлежит агенту, если его id есть в составе. Состав симметричен, и хранение его внутри `buildGuide` каждого участника означало бы три копии одного и того же, которые рано или поздно разъезжаются. Отряд в ZZZ всегда из трёх агентов — это зашито в схему (`length(3)` + запрет повторов), как и уникальность состава по набору участников. Кроме участников, в составе ничего не хранится: название и комментарий были придуманными подписями к тройке портретов — их приходилось сочинять на каждый состав, и они же ломали одинаковую высоту карточек.

**Битая ссылка на участника роняет сборку.** `getTeamsForCharacter` бросает ошибку с перечнем участников состава и неизвестным id, тогда как `getTierBoard` запись на несуществующего агента молча пропускает. Разница намеренная: тир-лист и карточки наполняются независимо, а состав из двух участников — не команда, а ссылка в никуда. Страницы агентов статические, поэтому опечатка в id падает на `npm run build`, а не превращается в мёртвый элемент на странице.

**Карточка состава живёт в `entities/team`, а портрет — в `shared/ui`.** Один и тот же состав показывают гайд агента и страница `/teams`, поэтому карточка не может остаться внутри виджета: виджеты друг друга не видят. Она переехала в сущность `team` — и потянула за собой портрет, который до этого лежал в `entities/character`, а импорт между слайсами одного слоя FSD запрещён. Портрет оказался не про персонажа, а про картинку в рамке с заданными пропорциями, так что его место в `shared/ui/portrait.tsx`; вызывающая сторона задаёт рамку и скругление через `className`.

**Опции фильтров вычисляются из данных.** Списки атрибутов и специализаций собираются из самих персонажей, а не задаются константой: новый атрибут появляется в фильтрах сам, без правки кода. Фильтра по рангу нет — все агенты сейчас ранга S, выбор был бы бессмысленным; `Character.rarity` при этом остаётся в схеме и на карточке (`RarityBadge`), это только про фильтр.

**Портреты хранятся в репозитории.** `public/images/characters/<slug>.webp`, а не подгрузка с чужого CDN: чужой хост может отдать 404 или сменить схему адресов.

**Иконки специализаций и атрибутов тоже хранятся в репозитории.** `public/images/specialties/<key>.png` (семь) и `public/images/attributes/<key>.png` (семь: физический, огонь, лёд, электро, эфир, ветер, люмен) — скачаны с zenlesszonezero.wiki.gg (страница «Оружейник», блоки «Специальности» и «Атрибуты»), по той же причине, что и портреты. Из блока «Атрибуты» взяты только используемые в данных ключи — Мороз, Остриё и Аура-тушь не персонажный атрибут, а подтипы Льда/Электро/Эфира, своих значений `Character.attribute` для них нет. Путь не хранится словарём, а строится из ключа (`/images/<группа>/<key>.png`) в `getSpecialtyIcon` и `getAttributeIcon` в `shared/config/dictionaries.ts`; иконка есть только у ключа, для которого есть подпись, — для неизвестного фильтр показывает текст.

**Везде, где есть портрет агента, поверх него — иконка атрибута.** `CharacterCard`, `CharacterTile` (тир-лист) и портрет участника в `TeamCard` (`entities/team`) показывают `AttributeIconBadge` в правом верхнем углу: кружок с иконкой атрибута, рамка в цвете атрибута, тёмная полупрозрачная подложка (`bg-black/55` + `backdrop-blur-sm`) для контраста на любом портрете — без подписи, так плотные сетки (тир-лист, составы) не зашумляются текстом. Полноразмерный `AttributeBadge` с подписью остался только в шапке страницы агента ([character-details-page.tsx](../src/views/character-details/ui/character-details-page.tsx)) — там он один и не конкурирует за место с другими карточками.

**Бейдж атрибута и его стили — в `shared`, а не в `entities/character`.** `AttributeIconBadge` (`shared/ui/attribute-icon-badge.tsx`) и функции `getAttributeStyle`/`getAttributeBorderStyle` (`shared/lib/attribute-styles.ts`) нужны и `entities/character`, и `entities/team` — а слои `entities` друг у друга ничего не импортируют, поэтому общее переехало в `shared`, тем же приёмом, что раньше `Portrait` и `role-styles.tsx` (см. записи выше). Ради оверлея `Portrait` (`shared/ui/portrait.tsx`) научился принимать `children`, рендерит их поверх `Image` внутри уже существующего `relative`-контейнера. `getAttributeBorderStyle` возвращает только `border-attr-*`, без фона/текста из `getAttributeStyle`, — фон бейджа здесь тёмная подложка, а не цвет атрибута. Чтобы портрет участника состава мог показать иконку, `TeamMember` (`shared/api/teams.ts`) расширен полем `attribute`.

**Отступ бейджа атрибута на портрете участника — проп `TeamCard`, а не константа.** На `/teams` карточек состава много на экране одновременно, поэтому там бейдж прижат ближе к краю (`badgeInset="sm"`, передаётся из `TeamGrid`); в блоке «Команды» на странице агента карточек три и места больше — там действует отступ по умолчанию (`badgeInset` не передаётся, `TeamCard` берёт `'default'`). Значения — `top-0.5 right-0.5` (`sm`) и `top-1.5 right-1.5` (`default`) в `MemberPortrait` внутри `entities/team/ui/team-card.tsx`.

**Текущий агент в `TeamCard` не подсвечивается отдельно и не ссылается сам на себя.** Раньше `MemberPortrait` принимал `isCurrent` и рисовал такому участнику отдельную рамку/текст цвета `primary` — на фоне ховер-эффектов по цвету атрибута у остальных двух это смотрелось рассогласованно. Теперь `isCurrent` убран: рамка/тень/текст у всех троих одинаковые, по атрибуту (`getAttributeGroupHoverBorderStyle` и соседние `group-hover`-функции из `shared/lib/attribute-styles.ts`), а разница только в обёртке — `Link` для остальных участников, обычный `div.group` для текущего агента (сохраняет тот же ховер, но без перехода).

**Карточка состава не поднимается при наведении, только подсвечивается тенью.** `hover:-translate-y-0.5` убран с контейнера `TeamCard` — в сетке из нескольких карточек в ряд независимый вертикальный сдвиг наведённой карточки выглядел дёрганым. `hover:shadow-lg` и рамка `hover:border-primary/30` остались единственными ховер-индикаторами блока.

## Взаимодействие

**Состояние фильтров живёт в query-параметрах.** Ссылку с выбранными фильтрами можно скопировать и переслать, кнопка «назад» работает штатно, состояние переживает перезагрузку. Чтение и запись — общий хук `useQueryState(fields)` в `shared/lib/use-query-state.ts`; фичи только сопоставляют поля с именами параметров и проверяют значения.

**Строка поиска пишется в URL без `trim`.** Поле ввода контролируемое и читает значение обратно из URL, поэтому раньше trim при записи съедал пробел прямо во время набора: «Е Шунь» превращалось в «ЕШунь», и имя из нескольких слов было не найти. Теперь в URL лежит введённое как есть, а нормализация (trim, нижний регистр) — только в функции фильтрации. Строка из одних пробелов параметр удаляет.

**Значения из URL проверяются.** `?damageType=` приходит от пользователя как угодно: неизвестное значение превращается в `null` (`isTeamDamageType`), а не в фильтр, под который не подходит ни один состав. Список типов и guard лежат в `shared/config`, а не берутся из zod-схемы: импорт значения из `@/shared/api` в клиентский компонент затащил бы в бандл zod и сами `data/*.json`. Из `shared/api` клиентские компоненты берут только типы.

**`useQueryState` не реэкспортируется из `shared/lib/index.ts`.** Этот barrel импортируют серверные компоненты ради `cn`, а хуки `next/navigation` в их граф попадать не должны — сборка падает. Хук импортируется напрямую, `@/shared/lib/use-query-state`, как и компоненты `shared/ui`.

**Общая разметка фильтров — в `shared/ui/filter-controls.tsx`.** `FilterSearch` (поиск + «Сбросить») и `FilterToggleGroup` (группа с пунктом «Все» и маппингом «Все / повторный клик → `null`») используются обеими фичами фильтров, а импорт между фичами запрещён. Там же, в `shared/ui`, — `empty-state.tsx`, общая заглушка пустых списков.

**`filter-characters` переиспользуется на тир-листе.** Отдельная фича `filter-tierlist` из спецификации не понадобилась: тир-лист фильтрует записи, но самого персонажа внутри проверяет тем же предикатом `matchesCharacterFilters(state)` (на нём же построен `applyCharacterFilters`). Дублировать логику фильтрации ради формального соответствия плану смысла нет — это осознанное расхождение со [SPEC.md](../SPEC.md).

**У команд — отдельная фича `filter-teams`, а не переиспользование `filter-characters`.** Состав фильтров разный по смыслу: поиск по имени агента ищет по всем трём участникам состава (`team.members.some(...)`), а не по одному полю `name`, как у персонажа; второй фильтр — `damageType` состава, которого у `Character` вообще нет. Общей структуры для переиспользования не набралось, зато сохранился тот же паттерн: query-параметры (`agent`, `damageType`), чистая функция `applyTeamFilters` + `isFilterActive`, клиентский `TeamsContent` за границей `Suspense`, чтобы `/teams` осталась статической страницей.

**Источник перехода передаётся в `?from=`, а не берётся из истории браузера.** Кнопка «назад» на странице агента ведёт туда, откуда пришли, и ведёт себя одинаково при открытии ссылки в новой вкладке. Источники — `tierlist`, `characters`, `teams` (`backSources` в `shared/config/routes.ts`); без параметра кнопка ведёт к списку агентов. Карточка состава получает источник пропом `from`: на `/teams` его передаёт `TeamGrid`, а в гайде агента переход к напарнику идёт без него — возврат «в команды» там был бы ложным.

**`scrollbar-gutter: stable` на `html`.** Страницы разной высоты иначе сдвигают контент по горизонтали при переходе между теми, где вертикальный скроллбар появляется, и теми, где нет. Полоса под скроллбар зарезервирована всегда, вместо старого хака `overflow-y: scroll`.

**Фильтры по специализации и атрибуту — иконки в `ToggleGroup`, а не `Select`.** По семь значений на каждый, умещаются на экране, и с иконками узнаются быстрее подписи в выпадающем списке. Каждый — отдельная строка (специализация и атрибут не смешиваются в один флекс-ряд с поиском), у обоих `*` — отдельный пункт группы, соответствующий отсутствию фильтра (`specialty: null` / `attribute: null`); клик по уже выбранной иконке тоже снимает фильтр — так работает несобираемый (`type="single"`) `ToggleGroup` из shadcn/radix по умолчанию.

**Фильтр типа урона у команд — тот же `ToggleGroup`, вместо `Select`, и раскрашен под бейдж.** Всего два значения (`pure-dps`, `anomaly-dps`) — выпадающий список был явно избыточен рядом с иконками специализации/атрибута на странице персонажей. Кнопка показывает ту же иконку роли, что и бейдж на карточке состава (`renderRoleIcon`), а при выборе перекрашивается в её же цвет — `getRoleToggleStyle` в `shared/lib/role-styles.tsx` держит те же классы `border/bg/text`, что и `getRoleBadgeStyle`, но с префиксом `data-[state=on]:`, чтобы применялись только к выбранной кнопке. Префикс дописан отдельным литералом в объекте, а не собран из `getRoleBadgeStyle(...)` через шаблонную строку в рантайме — Tailwind ищет имена классов в исходниках текстовым сканированием и не находит то, что появляется только после конкатенации.

**Навигация в шапке на мобильных — боковое меню (`Sheet`), а не горизонтальный скролл.** Ниже брейкпоинта `sm` строка ссылок в [site-header.tsx](../src/widgets/header/ui/site-header.tsx) скрыта (`hidden sm:flex`), вместо неё — кнопка-гамбургер, открывающая `Sheet` со списком ссылок; ссылка-тайтл «ZenlessGuide» при этом всегда остаётся в шапке, а не дублируется внутри меню. Открыт/закрыт — управляемое состояние (`useState`) в самом компоненте, а не `SheetTrigger`: кнопка одна и та же и для десктопа не нужна отдельная разметка. `SheetTitle` оставлен (`sr-only`) только ради `aria-describedby`/a11y-контракта Radix Dialog, который требует доступного заголовка у контента, даже если визуально в меню заголовка нет. Клик по ссылке в меню закрывает его (`onClick` дополнительно к переходу), иначе `Sheet` оставался бы открытым поверх новой страницы. На `sm` и шире, наоборот, видна горизонтальная `nav` (как раньше), а кнопка меню скрыта (`sm:hidden`); у самой `nav` скроллбар по-прежнему спрятан визуально (`scrollbar-width: none` + `::-webkit-scrollbar { display: none }`) на случай, если ссылки не поместятся по ширине.

**Сторона бокового меню — переключатель внутри самого меню, сохраняется в `localStorage`.** По умолчанию `Sheet` открывается справа (`menuSide: "right"`); внизу меню — `Switch` (shadcn/radix) между иконками `PanelLeftIcon`/`PanelRightIcon`, активная иконка подсвечена `text-foreground`, неактивная — `text-muted-foreground`. Выбор пишется в `localStorage` под ключом `zenless-guide:menu-side` и читается лениво в инициализаторе `useState` — `typeof window === "undefined"` возвращает дефолт «справа» при серверном рендере. Гидратационного расхождения при этом не возникает: `Sheet` закрыт при первом рендере, и сторона влияет только на DOM внутри `SheetContent`, который Radix не монтирует, пока меню не открыто, — то есть SSR-разметка от стороны не зависит. Обёртка блока (`div` с иконками, подписью и `Switch`) выравнивается по той же стороне, что и сам `Sheet` (`items-end` при `menuSide === "right"`, иначе `items-start`) — так управление стороной визуально «прилипает» к краю, у которого открывается меню. **Сторона применяется так же, как тема: после анимации свитча.** Клик сначала пишет `pendingSide`, по которому анимируются свитч и иконки. Через `SWITCH_TRANSITION_MS` (экспортируется из `shared/ui/switch.tsx`, общий с переключателем темы) сторона применяется и сохраняется. Панель к другому краю переставляется мгновенно (`left`/`right` не анимируются), поэтому на новом месте она коротко въезжает от края через Web Animations API (`element.animate`, 200мс) — так же, как при открытии. Пересоздать `SheetContent` через `key`, чтобы заново проиграть CSS-анимацию открытия, отвергли: вместе с панелью пересоздаётся и оверлей, и его размытие фона мигает.

**Переключатель темы — `Switch` между `Sun`/`Moon`, а не кнопка с иконкой.** [theme-toggle.tsx](../src/widgets/header/ui/theme-toggle.tsx): `checked` = тёмная тема. В отличие от стороны меню, тему нельзя прочитать лениво при инициализации — её знает только `next-themes` через `useTheme()`, а на сервере она в принципе не определена (тема применяется инлайн-скриптом до гидратации, чтобы не было мигания). Поэтому `checked` до маунта всегда `false`: `useMounted()` — небольшая обёртка над `useSyncExternalStore` (`getSnapshot` → `true`, `getServerSnapshot` → `false`), которая возвращает `true` только после гидратации на клиенте. Чтобы в тёмной теме при загрузке бегунок не прыгал с солнца на луну, **положение свитча до гидратации задаёт CSS, а не React**. Обёртка помечена `data-slot="theme-toggle"`, `data-mounted` появляется после маунта. Правило `.dark [data-slot="theme-toggle"]:not([data-mounted])` в `globals.css` показывает «тёмное» положение: цвет трека, `transform` бегунка, цвета иконок. Класс `dark` на `<html>` к этому моменту уже поставлен скриптом `next-themes`. Правило вне `@layer`, поэтому перебивает утилиты Tailwind; `transform` стоит с `!important`, иначе его перебил бы инлайн-стиль бегунка. После гидратации состояние React даёт те же значения, и переходам нечего анимировать. Отвергнутые варианты: прятать свитч до маунта — он «проявлялся» бы с задержкой; рендерить на сервере «тёмное» положение по `defaultTheme` — тогда мерцание переехало бы к тем, у кого выбрана светлая тема. Это осознанно не `useEffect` + `setState` (частый паттерн для той же задачи) — такая связка даёт лишний каскадный ре-рендер и падает под `eslint-plugin-react-hooks` (`react-hooks/set-state-in-effect`) в этом проекте. **Цвета свитча темы зависят от его положения, а не от текущей темы.** Трек, бегунок и иконки красятся токенами `--theme-toggle-*` из `globals.css`: они заданы только в `:root` и в `.dark` не переопределяются. Трек фиолетовый в обеих темах, в каждом положении повторяет `--primary` своей темы (блёклый `bg-input` из `shared/ui/switch.tsx` терялся на светлом фоне). Бегунок светлый. Активная иконка: солнце жёлтое, луна бледно-голубая (лунный свет). Неактивная — нейтральный серый. Обычные `bg-primary`, `dark:`-классы и `muted-foreground` не подходят: тема применяется уже после анимации, при отключённых переходах, и свитч перекрашивался рывком. `dark:`-варианты в классах трека и бегунка стоят только затем, чтобы перебить `dark:data-*`-цвета базового компонента. Для этого у `Switch` появился проп `thumbClassName`. Иконки анимированы синхронно со свитчем только цветом (`transition-colors duration-300`) — ни поворота (`rotate`), ни масштабирования (`scale`) у солнца и луны нет: оба варианта пробовали, но по итогу убрали у обеих иконок целиком, решили, что лишнее движение отвлекает и не читается как часть анимации. **Тема применяется с задержкой в длительность анимации свитча (300мс).** `ThemeProvider` включает `disableTransitionOnChange`: на время `setTheme` `next-themes` вставляет `* { transition: none !important }`, и бегунок с иконками перескакивали мгновенно. Поэтому клик сначала пишет локальное `pendingDark` (свитч и иконки анимируются по нему), а `setTheme` вызывается по таймеру (`SWITCH_TRANSITION_MS`) после окончания перехода; повторный клик сбрасывает таймер. Снять `disableTransitionOnChange` глобально отвергли: тогда все элементы с `transition-colors` перекрашиваются вразнобой и страница «плывёт» при смене темы.

**У `Switch` (`shared/ui/switch.tsx`) переход бегунка и трека — 300мс с `ease-out`, а не дефолтные Tailwind ~150мс.** Базовый shadcn-компонент задаёт `transition-transform`/`transition-all` без явной длительности; здесь она прописана прямо в примитиве (`duration-300 ease-out` и у трека, и у бегунка), чтобы переключение выглядело плавным «слайдом», а не резким скачком — это касается обоих свитчеров в шапке (темы и стороны меню), а не только одного из них, поскольку компонент общий.

**Позиция бегунка `Switch` задаётся инлайн-стилем (`style={{ transform: ... }}`), а не только CSS-классами `data-checked:`/`data-unchecked:`.** Изначально бегунок двигали исключительно Tailwind-классы вида `group-data-[size=default]/switch:data-checked:translate-x-[calc(100%-2px)]` — сам по себе корректный CSS (подтверждено через `CSSOM`: селектор матчится, объявление верное), но в части браузерных движков стиль по смене атрибута `data-state` на повторных переключениях иногда не пересчитывался, и бегунок застревал на месте. `checked` уже приходит пропом в оба свитчера (управляемый режим), поэтому в `shared/ui/switch.tsx` он прокидывается дальше и параллельно с классами пишется как `style` на `SwitchPrimitive.Thumb` — инлайн-стиль не зависит от инвалидации по атрибуту и обновляется вместе с каждым React-рендером напрямую. CSS-классы остаются рабочим фолбэком для гипотетического неуправляемого использования (`defaultChecked` без `checked`) и **обязаны** двигать то же самое свойство `transform` через `[transform:translateX(...)]` (а не Tailwind-утилиту `translate-x-*`, которая пишет в отдельное CSS-свойство `translate`) — иначе инлайн-стиль и класс не перекрывают, а складывают смещения, и бегунок съезжает на сумму обоих.

**Обёртки свитчеров в шапке — `<div>`, а не `<label>`.** И в [theme-toggle.tsx](../src/widgets/header/ui/theme-toggle.tsx), и у блока стороны меню в [site-header.tsx](../src/widgets/header/ui/site-header.tsx) `Switch` — это `<button role="switch">`, не `<input>`; `<label>` вокруг такой кнопки не даёт пользы (нет `for`-ассоциации с полем), а в части браузеров дублирует клик — сначала как обычный клик по кнопке, потом как перенаправленный от `<label>`. Имя для скринридера уже даёт `aria-label` на самом `Switch`, отдельный `sr-only`-текст в обёртке был лишним.
